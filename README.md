# نظام إدارة المطاعم (RMS)

نظام إلكتروني متكامل لإدارة المطعم، مبني بنفس فكرة وبنية نظامَي **إدارة المدارس (SMS)** و**إدارة المستشفيات (HIS)**:
هرم تنظيمي واضح، صلاحيات حسب الدور (RBAC)، سجل تدقيق لكل عملية حساسة، وواجهة عربية RTL.

يتكوّن من ثلاثة أنظمة تعمل على قاعدة بيانات واحدة:

| النظام | الوصف | من يستخدمه |
|---|---|---|
| **إدارة المطعم** | لوحة تحكم، تقارير المبيعات، مخزون بوصفات تُخصم تلقائيًا، موظفون، سجل تدقيق، إعدادات الضريبة/الخدمة | المالك، المدير |
| **نظام المنيو** | تصنيفات وأصناف وإضافات وصور، "نفد/متوفر"، **منيو عام للزبون عبر QR** على كل طاولة | المدير (إدارة) + الزبون (عرض وطلب) |
| **نظام الكابتن** | خريطة الطاولات بالألوان، أخذ الطلب، إرسال للمطبخ، الموافقة على طلبات الزبائن، الفاتورة، نقل الطاولة؛ + **شاشة المطبخ (KDS)** + **الكاشير** | الكابتن، المطبخ، الكاشير |

## المقابلة مع نظامَي المدارس والمستشفيات

| SMS (مدارس) | HIS (مستشفى) | RMS (مطعم) |
|---|---|---|
| مديرية التربية | — | **المالك** (يرى كل الفروع) |
| المدرسة | المستشفى | **المطعم/الفرع** |
| الصف ← الشعبة | القسم ← السرير | **القاعة ← الطاولة** |
| الطالب | المريض | **الطلب (Order)** |
| المواد/المنهج | الخدمات الطبية | **المنيو (تصنيف ← صنف)** |
| الحضور والغياب | المواعيد | **حالة الطاولة والطلب** |
| الأقساط والمحاسبة | الفوترة والتأمين | **الفواتير والدفع (نقد/بطاقة/مقسّم)** |
| الصيدلية/المخزون | المخزون | **المخزون + الوصفات** |
| مدير/معاون/مدرّس/ولي أمر | مدير/استقبال/طبيب/ممرض | **مالك/مدير/كاشير/كابتن/مطبخ** |
| رمز QR للطالب | — | **رمز QR لكل طاولة** |
| سجل التدقيق | سجل التدقيق | **سجل التدقيق** |

## دورة الطلب

```
الزبون يمسح QR ──► أصناف "بانتظار الموافقة" ──► الكابتن يوافق ──┐
الكابتن يفتح الطاولة ويختار الأصناف ─────────────────────────────┤
                                                                  ▼
                    المطبخ/البار/الحلويات (حسب محطة التصنيف): انتظار ► تحضير ► جاهز
                                                                  ▼
                              الكابتن يقدّم ► يطلب الفاتورة ► الكاشير يدفع
                                                                  ▼
                       الطاولة "تنظيف" ► فارغة · خصم المخزون · تقارير · تدقيق
```

## الأدوار والصلاحيات

| الدور | الصلاحيات |
|---|---|
| `owner` | كل شيء على كل الفروع |
| `manager` | كل شيء في فرعه: منيو، طاولات، مخزون، تقارير، موظفون (عدا المدراء)، إلغاء الطلبات |
| `cashier` | الفواتير والدفع والخصم، التقارير، رؤية الطلبات |
| `captain` | الطاولات، أخذ الطلبات، الموافقة على طلبات QR، طلب الفاتورة، التقديم |
| `kitchen` | شاشة المطبخ فقط (لا يصل لسجل الطلبات ولا الفواتير ولا التقارير) |

قواعد أمان وتشغيل مطبّقة على الخادم (وليس في الواجهة فقط):
- الأسعار تُقرأ دائمًا من المنيو في قاعدة البيانات — لا يُوثَق بسعر مرسل من العميل.
- لقطة (snapshot) للاسم والسعر في كل صنف طلب، فلا يتغير الطلب القديم بتعديل المنيو.
- طلب واحد مفتوح لكل طاولة (قفل على مستوى الصف داخل معاملة) — لا طلبات مكررة عند ضغط كابتنين معًا.
- أصناف الزبون (QR) لا تُحسب ولا تصل المطبخ قبل موافقة الكابتن؛ والمسارات العامة محدودة المعدل.
- إلغاء صنف مُرسل يتطلب سببًا؛ وبعد بدء التحضير يتطلب مديرًا. الخصم للكاشير/المدير فقط.
- الدفع يقبل دفعات متعددة ويجب أن يغطي الإجمالي؛ لا دفع مزدوج.
- كلمات المرور الضعيفة/المؤقتة تُجبر على التغيير قبل أي استخدام للنظام.

## التقنيات

- **Backend**: Node.js + Express + Sequelize + PostgreSQL + JWT
- **Frontend**: React + Vite + React Router — واجهة عربية RTL بتصميم زجاجي بروح macOS: شريط قوائم علوي بساعة حيّة، Dock بتكبير الأيقونات وقفزة الفتح، نوافذ بأزرار macOS الحقيقية (إغلاق / تصغير إلى الـ Dock بتأثير الجني / ملء الشاشة، ونقرتان على شريط العنوان للتكبير)، شاشة دخول كشاشة القفل مع اهتزاز عند الخطأ، لمعة زجاج تتبع المؤشر، حركات نابضية وعدّادات متحركة، ووضع فاتح/داكن/تلقائي، بخط Times New Roman. تحترم إعدادات تقليل الحركة والشفافية، والطباعة بلا تأثيرات.
- التحديث الحي للمطبخ والكابتن بالاستعلام الدوري كل 4–5 ثوانٍ (بدون WebSocket لتبسيط النشر)

## طرق التشغيل: موقع إلكتروني أو نظام محلي بلا إنترنت

النظام نفسه يعمل بثلاث طرق، حسب ما يناسب المطعم:

| الطريقة | متى تناسب | الإنترنت |
|---|---|---|
| **1. موقع إلكتروني** على خادم سحابي ودومين (HTTPS) | عدة فروع، أو الإدارة من خارج المطعم | مطلوب، مع تحمّل الانقطاعات القصيرة (انظر PWA أدناه) |
| **2. خادم محلي** على جهاز داخل المطعم | الإنترنت ضعيف أو غير متوفر | **غير مطلوب**: الأجهزة تتصل بالجهاز عبر شبكة Wi‑Fi المطعم |
| **3. تطبيق مثبّت (PWA)** من المتصفح على الجوال/التابلت/الكمبيوتر | فوق أي من الطريقتين | يفتح ويعمل عند انقطاع الاتصال |

### المتطلبات
Node.js 18+ و PostgreSQL 14+ (أو Docker).

### الطريقة 2: خادم محلي بأمر واحد (بدون إنترنت)
```bash
npm run install:all        # مرة واحدة
cp backend/.env.example backend/.env   # بيانات قاعدة البيانات (أنشئ قاعدة restaurant_rms)
npm run seed               # ⚠️ يعيد إنشاء الجداول ويعبّئ مطعمًا تجريبيًا — للتجربة فقط
npm run local              # يبني الواجهة ويشغّل كل النظام على المنفذ 4000
```
الخادم يقدّم الواجهة بنفسه (بدون nginx)، فتفتح الأجهزة على شبكة المطعم: `http://IP-الجهاز:4000`
(مثل `http://192.168.1.10:4000`). اجعل عنوان IP للجهاز ثابتًا من إعدادات الراوتر.

### الطريقة 1: موقع إلكتروني
- **Docker**: `docker compose up --build` ثم `docker compose exec backend npm run seed` لأول مرة، وضع أمامه خادم HTTPS (Caddy أو Nginx مع Let's Encrypt) على دومينك.
- **بدون Docker**: نفس أوامر الطريقة 2 على الخادم السحابي خلف HTTPS. غيّر `JWT_SECRET` وكلمات مرور قاعدة البيانات.

### الطريقة 3: التثبيت كتطبيق والعمل بدون اتصال (PWA)
من Chrome/Edge: زر "تثبيت" في شريط العنوان. ومن Safari على iPhone: مشاركة ← "إضافة إلى الشاشة الرئيسية".

ما يعمل عند انقطاع الاتصال:
- **فتح النظام** وعرض **آخر بيانات محفوظة** (الطاولات، المنيو، الطلبات، المطبخ). شريط القوائم يعرض "غير متصل" أو "بيانات محفوظة".
- **أخذ طلبات الكابتن:** يُحفظ الطلب على الجهاز ("⏳ بانتظار الاتصال") ويُرسل للمطبخ تلقائيًا عند عودة الشبكة.
  الخادم يمنع التكرار (ترويسة `Idempotency-Key`)، فلا يتكرر الطلب حتى لو أُعيد إرساله بعد ضياع الرد.
  إن رفض الخادم الطلب عند عودة الاتصال (مثلًا صنف نفد) يظهر إشعار بالسبب.
- يتطلب اتصالًا: الدفع، والخصم، وإلغاء الأصناف، والموافقة على طلبات QR، والتقارير الحيّة.
- عند تسجيل الخروج تُحذف البيانات المحفوظة من الجهاز. الطلبات غير المرسلة تبقى وتُرسل عند دخول نفس المستخدم.

### الخادم المحلي مع HTTPS عبر Caddy (موصى به للمطعم)
المتصفحات لا تفعّل العمل بدون اتصال ولا تثبيت التطبيق إلا على **HTTPS**. لذلك يأتي المشروع مع إعداد Caddy جاهز في `deploy/local/`
يصدر شهادة من **مرجع شهادات محلي خاص بالمطعم**، ولا يحتاج إنترنت ولا دومين.

**بأمر واحد عبر Docker** (قاعدة البيانات + النظام + Caddy):
```bash
cd deploy/local
cp .env.example .env      # ضع RMS_HOST = عنوان IP الثابت لهذا الجهاز، وكلمات سر قوية
docker compose up -d --build
docker compose exec app npm run seed   # ⚠️ للتجربة فقط: يعبّئ بيانات تجريبية ويمسح الموجود
```

**بدون Docker** (بعد `npm run local` من الطريقة 2):
- Linux / macOS: `sudo RMS_HOST=192.168.1.10 ./deploy/local/run-caddy.sh`
- Windows (PowerShell كمسؤول، بعد `winget install CaddyServer.Caddy`): `.\deploy\local\run-caddy.ps1 -RmsHost 192.168.1.10`

**إعداد كل جهاز (مرة واحدة):** افتح `http://192.168.1.10/` على الجوال أو التابلت أو الكمبيوتر.
- تظهر **صفحة إعداد** فيها زر تنزيل شهادة المطعم، وخطوات تثبيتها لأندرويد وiPhone وويندوز وماك.
- بعد التثبيت تكتشف الصفحة ذلك وتحوّل تلقائيًا إلى `https://192.168.1.10/`، ومن هناك يمكن **تثبيت النظام كتطبيق**.
- أي عنوان آخر عبر http يتحول تلقائيًا إلى https.

ملاحظات:
- مجلد بيانات Caddy (`caddy_data` في Docker، أو `deploy/local/caddy-data` بدونه) يحفظ مرجع الشهادات، وهو صالح 10 سنوات. **انسخه احتياطيًا**، فحذفه يعني إعادة تثبيت الشهادة على كل الأجهزة.
- ثبّت عنوان IP للخادم من إعدادات الراوتر (DHCP reservation). تغيّر العنوان يعني إصدار شهادة جديدة، وهذا يتم تلقائيًا، لكن يجب تحديث `RMS_HOST`.
- الخادم يثق بترويسة `X-Forwarded-For` من عناوين الشبكة المحلية فقط (`TRUST_PROXY`)، حتى يعمل تحديد المعدل لطلبات QR لكل زبون على حدة.

## تطبيق الكابتن (Android)

تطبيق أصلي بـ Kotlin + Jetpack Compose في مجلد `android/` بنفس نمط تطبيقَي SMS وHIS (HttpURLConnection + org.json + SharedPreferences + ViewModel واحد، واجهة عربية RTL).

- تسجيل الدخول (مع إعداد عنوان الخادم) وتغيير كلمة المرور الإجباري.
- خريطة الطاولات بالألوان مع تنبيهات: 🔔 نداء الزبون، ✅ صنف جاهز، 📱 طلب زبون (QR) بانتظار الموافقة. تتحدث تلقائيًا كل 5 ثوانٍ طالما التطبيق ظاهر، مع شريط "لا يوجد اتصال".
- شاشة الطاولة: الطلب الحالي، الموافقة على أصناف QR، "قدّمت" للأصناف الجاهزة، إلغاء بسبب، طلب الفاتورة/إعادة الفتح، نقل الطلب لطاولة فارغة، تلبية النداء.
- إضافة أصناف من المنيو (تصنيفات + بحث + إضافات) إلى سلة فيها كمية وملاحظة للمطبخ وعدد الضيوف، ثم إرسال واحد للمطبخ.
- الأدوار المسموحة: كابتن، كاشير، مدير، مالك (المطبخ يستخدم شاشة الويب).

الفتح والتشغيل: افتح مجلد `android/` في Android Studio (أو `gradle :app:assembleDebug` مع تثبيت Android SDK). على المحاكي يكون عنوان الخادم الافتراضي `http://10.0.2.2:4000`؛ وعلى جهاز حقيقي أدخل عنوان IP لجهاز الخادم من "إعدادات الخادم" في شاشة الدخول.

> **حالة التحقق:** طبقة البيانات (`data/`) مختبرة فعليًا على الخادم الحقيقي عبر `android/datalayer-test` (بدون Android SDK):
> `cd backend && npm run seed && npm run dev` ثم `cd android/datalayer-test && gradle run` (أعد `npm run seed` قبل كل تشغيل).
> أما واجهة Compose (`ui/`) فكُتبت ودُقّقت يدويًا لكنها **لم تُجمَّع ولم تُشغَّل بعد** لعدم توفر Android SDK في بيئة التطوير؛ توقّع أن تحتاج تعديلات طفيفة عند أول بناء في Android Studio.
